# 最新分账业务场景与历史需求偏离对比

> 审计日期：2026-06-11  
> 审计口径：以当前代码、数据库初始化脚本、后台 OpenAPI 和离线自动化测试作为“当前实现事实”；以历史需求文档作为对比基线。  
> 注意：历史文档包含多个阶段方案，已被后续文档明确废弃的设计不认定为缺陷，而认定为“已确认架构演进”。

## 1. 审计结论

当前分账业务已从历史最初的三种模式，演进为四种规则模式、统一独立新表、规则级结算周期和完整支付生命周期。

总体判断：

- 核心业务目标已实现，并补充了商品差异化分账、固定金额、全额、跨阶梯拆分、渠道开关、T+N 结算等能力。
- `strategy_payee`、旧分账策略和旧分账结果表保持隔离，属于后续明确确认的架构演进，不属于需求偏离。
- 当前存在 2 项需要业务明确决策的需求偏离：
  1. `revenue_rule.payer_ao_id` 保留在配置、接口和文档中，但完全不参与规则匹配。
  2. `rule_mode=3` 设备分账只生成规则命中的金额，未分配余额不会继续进入普通分账；历史文档未统一明确该余额归属。
- 当前存在 3 项实现与建议方案不一致，但尚不构成明确缺陷：
  1. `base_type` 默认值为 `1`（订单总额），历史建议默认使用 `2`（扣除出租分账金额）。
  2. 组织管理员按收款组织或接收组织查看分账订单的权限口径尚未实现，当前主要按账户管理人隔离。
  3. 历史需求曾要求退款尾差由最后一笔吸收，当前未发现对应确定性实现和专项测试。

## 2. 当前权威业务边界

### 2.1 与旧业务的边界

- 原收款策略继续由 `strategy_payee/sp_id` 负责。
- 新分账只读取订单最终确定的 `sp_id`、支付类型和收款结果。
- 新分账不得新增、修改、删除 `strategy_payee` 数据。
- 新分账配置和结果只写入 `revenue_*` 表。
- `revenue_pay_channel` 仅控制支付渠道是否触发新分账。
- 结算周期归属实际命中的 `revenue_rule`。
- 分账结果统一写入 `revenue_order`，不写入旧分账结果表。

### 2.2 当前计算顺序

1. 判断支付渠道是否启用新分账；未启用则清理待支付分账记录并跳过。
2. 计算 `rule_mode=2` 设备出租分账。
3. 计算 `rule_mode=4` 设备商品分账。
4. 商品规则没有命中任何商品时，回退执行 `rule_mode=3` 设备分账。
5. 没有命中商品规则和设备规则时，执行 `rule_mode=1` 普通分账。
6. 商品分账命中后，未分配余额继续执行普通分账。
7. 保存前检查订单分账总额和子订单分账总额不得超额。

## 3. 最新支持的分账业务场景

| 模式/阶段 | 当前支持场景 | 关键规则 |
| --- | --- | --- |
| 渠道开关 | 支付渠道启用或停用新分账 | 未命中启用渠道时不生成 `revenue_order`，支付继续 |
| `rule_mode=1` 普通分账 | 百分比、全额 | 必须完整分配订单剩余金额，否则支付前报错 |
| `rule_mode=2` 设备出租 | 百分比、固定金额、全额 | 商品组织与订单收款组织不同时触发；未配置出租规则或商品组织明细时严格报错 |
| `rule_mode=3` 设备分账 | 百分比、固定金额、全额、阶梯百分比 | 可按订单总额或扣除出租分账后的金额计算 |
| `rule_mode=3` 阶梯口径 | 净营业额、支付成功金额 | 使用设备月度营业额，支持整单命中和跨阶梯拆分 |
| `rule_mode=4` 设备商品分账 | 商品金额百分比、按件固定金额 | 按设备和商品匹配；商品未命中时回退设备分账；命中后剩余金额进入普通分账 |
| 结算周期 | 即时、T+N | 每条规则独立配置，生成分账订单时保存快照 |
| 支付状态 | 待支付、已结算、待结算、失败、已取消 | 支付成功即时结算或进入待结算；取消时更新状态 |
| 延期结算 | 到期定时结算 | 处理 `status=2` 且已到计划时间的记录 |
| 退款 | 按原分账记录冲减 | 更新 `refund_amount`，已结算余额型账户同步扣减 |
| 查询与导出 | 列表、详情、导出 | 普通账户管理人按 `manager_id` 隔离，审核账号可查看更大范围 |

## 4. 与历史需求逐项对比

### 4.1 已实现且一致

| 历史需求 | 当前实现 | 判断 |
| --- | --- | --- |
| 支持普通分账、设备出租、设备分账 | 三种基础模式均已实现 | 一致 |
| A 设备销售 B 商品时识别出租分账 | 按 `sod_ao_id != order.ao_id` 识别，并读取出租规则 | 一致 |
| 出租分账比例可配置，缺少配置时严格报错 | 支持比例并采用严格模式 | 一致 |
| 设备分账支持 B 20%、C 30% 等多个接收方 | 支持多个规则明细，比例合计受限 | 一致 |
| 出租与设备分账可并存，并允许扣除出租金额 | `base_type=2` 时按订单金额减出租分账金额 | 一致 |
| 支付渠道可控制是否生成新分账 | `revenue_pay_channel` 已实现渠道开关 | 一致 |
| 分账总额不得超过订单金额 | 保存前执行订单和子订单超额校验 | 一致 |
| 已结算或已退款记录不得被重算覆盖 | 仅删除 `status=0`，存在非待支付记录时拒绝重算 | 一致 |
| 分账结果保存账户、管理人、组织和规则快照 | `revenue_order` 保存完整快照 | 一致 |
| 普通账户管理人只能查看自己管理的分账订单 | 查询统一按当前 `manager_id` 过滤 | 一致 |
| 即时和 T+N 结算 | 规则级结算配置和延期任务已实现 | 一致 |

### 4.2 已确认的架构演进，不属于偏离

| 历史方案 | 当前方案 | 演进原因 |
| --- | --- | --- |
| 扩展 `strategy_payee` 保存默认分账账户 | 不修改 `strategy_payee`，独立维护新分账规则和账户 | 后续文档明确要求新旧业务隔离 |
| 使用 `revenue_payee_config` 控制收款策略是否分账和结算周期 | 已删除 `revenue_payee_config`；渠道控制触发，规则控制结算周期 | 配置责任收敛，避免按 `sp_id` 重复维护 |
| 扩展 `sale_orders_revenue` 作为权威结果表 | 使用独立 `revenue_order` | 新分账与旧分账结果彻底隔离 |
| 普通分账无需额外规则或依赖收款策略默认账户 | 普通分账必须绑定 `rule_mode=1` 规则及明细 | 普通分账也进入统一规则模型，剩余金额必须可解释 |
| 只有三种分账模式 | 新增 `rule_mode=4` 设备商品分账 | 后续新增的设备商品差异化分账需求 |
| 阶梯只支持本单后累计整单命中 | 同时支持整单命中和跨阶梯拆分 | 后续能力增强并已通过测试 |

### 4.3 能力扩展，需纳入最新需求基线

以下能力已经实现并通过测试，但在早期需求中未完整描述，建议作为最新正式需求保留：

| 扩展能力 | 当前实现 |
| --- | --- |
| 设备出租固定金额和全额模式 | `rule_mode=2` 支持 `calc_type=2/3` |
| 设备固定金额和全额模式 | `rule_mode=3` 支持 `calc_type=2/3` |
| 商品按件固定金额 | `rule_mode=4 + calc_type=2`，金额为单件值乘数量 |
| 商品规则未命中时回退设备规则 | 只有真正命中商品明细才抑制设备规则 |
| 同一订单不同规则使用不同结算周期 | 每条 `revenue_order` 保存实际命中规则的结算快照 |
| 全额规则唯一性 | 普通和设备规则中，全额明细不能与其他启用明细并存 |
| 停用备用规则绑定 | 同一设备可绑定同模式停用备用规则，仅限制启用规则唯一 |

## 5. 需求偏离与待决策项

### P1：`revenue_rule.payer_ao_id` 未参与规则匹配

历史需求：

- `payer_ao_id` 表示收款或代收组织。
- 设备出租策略希望支持按设备、收款组织、商品组织匹配。
- 后台原型要求配置收款或代收组织。

当前实现：

- 字段仍存在于数据库、模型、后台接口和 OpenAPI。
- 规则匹配只使用设备、`rule_mode` 和启用状态。
- `revenue_rule.payer_ao_id` 无论是否填写，都不会改变规则命中结果。
- `revenue_order.payer_ao_id` 仍有明确用途，保存订单实际收款组织快照，不应删除。

风险：

- 运营人员可能误以为配置的收款组织会限制规则适用范围。
- 同一设备如果未来可能使用不同收款组织，当前无法按收款组织选择不同规则。

建议决策：

- 若规则永远只按设备绑定：删除 `revenue_rule.payer_ao_id`，同步清理模型、接口、OpenAPI 和 SQL。
- 若同一设备需要按代收组织区分规则：保留字段，并在规则查询中增加 `payer_ao_id = order.ao_id` 或为空的匹配逻辑，同时明确优先级。

### P1：设备分账未分配余额归属未明确

历史需求：

- 早期设备分账示例只要求 B 20%、C 30%，没有明确剩余 50% 是否生成普通分账。
- 商品分账文档明确要求商品分账后剩余金额进入普通分账。
- 最新普通分账规则要求其命中时必须完整分配剩余金额。

当前实现：

- 商品分账命中后，剩余金额进入普通分账。
- 只有出租分账时，剩余金额进入普通分账。
- 一旦命中 `rule_mode=3` 设备分账，未分配余额不会进入普通分账。

风险：

- 如果设备规则只配置部分比例，订单金额会有一部分不生成任何新分账记录。
- 财务是否需要追踪该余额目前没有统一需求结论。

建议决策：

- 若设备分账只表示“额外分给指定接收方”，维持现状，并在需求中明确剩余金额不进入新分账。
- 若所有订单金额必须完整可追踪，设备分账后应将剩余金额交给普通分账。

### P2：设备分账默认基数与历史建议不同

历史建议：

- 出租与设备分账并存时，推荐默认 `base_type=2`，避免超额。

当前实现：

- 数据库和服务默认 `base_type=1`，即按订单总额计算。
- 支持显式配置 `base_type=2`。
- 保存前总额封顶会阻止超额分账。

判断：

- 属于默认值偏离，不是功能缺失。
- 可能导致运营忘记选择 `base_type=2` 时支付被超额校验阻断。

建议：

- 确认默认业务口径；若通常需要扣除出租金额，将数据库默认值、接口默认值和补全 SQL 统一改为 `2`。

### P2：组织管理员查询权限未完整落地

历史需求：

- 普通账户管理人只能查看自己的记录。
- 组织管理员可按本组织作为收款组织或接收组织查看记录，具体按角色权限配置。

当前实现：

- 非审核账号统一按当前 `manager_id` 过滤。
- 审核账号可查看更大范围。
- 未发现按组织角色自动追加 `payer_ao_id/receiver_ao_id` 范围的逻辑。

建议：

- 若组织管理员确实需要组织级视图，应补充权限模型和组织范围过滤。
- 若所有查看权限均以账户管理人为准，应更新历史需求，删除组织管理员视图描述。

### P2：退款尾差专项规则缺少证据

历史优化建议：

- 多次部分退款产生四舍五入差额时，最后一笔退款吸收尾差。

当前实现：

- 已支持退款冲减和商品固定金额按退款数量回退。
- 尚未发现“最后一笔退款吸收尾差”的明确实现和专项测试。

建议：

- 增加多次部分退款至全额退款的确定性测试，确认累计 `refund_amount` 最终准确等于应退分账金额。

## 6. 最新需求基线建议

建议将以下内容作为后续开发和验收的唯一需求基线：

1. 新分账与旧收款策略、旧分账数据完全隔离。
2. 渠道只负责是否触发新分账，规则负责计算和结算周期。
3. 支持 `rule_mode=1/2/3/4` 四种模式。
4. 规则优先级为：出租、商品、设备、普通；商品未命中时可回退设备规则。
5. 普通分账必须完整分配其负责的剩余金额。
6. 所有生成记录必须通过订单级和子订单级超额校验。
7. 已生成非待支付分账记录的订单不得重算覆盖。
8. 每条分账订单保存实际收款组织、接收组织、账户、管理人、规则和结算周期快照。
9. `revenue_order.payer_ao_id` 必须保留。
10. `revenue_rule.payer_ao_id` 和设备分账余额归属必须完成业务决策后再调整。
