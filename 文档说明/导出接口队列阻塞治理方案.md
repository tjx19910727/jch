# 导出接口队列阻塞治理方案

> 版本：v1.0 ｜ 适用分支：`uat` / `main_fix_stock`（可独立修复分支）｜ 适用库：`kiosk`
> 目标：解决"**导出内容过长导致 MQ 队列阻塞**"——把"数据随消息走"改为"**消息只传任务与查询条件**"，
> 消费端分片查询 + 流式生成 + 落盘下载，使单次导出不再独占队列、不再因大消息/大内存/重投而雪崩。

---

## 0. 结论摘要（TL;DR）

| 维度 | 现状 | 目标形态 |
|---|---|---|
| MQ 消息体 | 携带**整份导出数据**（`list`），随行数线性膨胀 | 只带 `{export_id, job_type, params}`，**恒定几百字节** |
| 消费并发 | `prefetch=1` + 单进程 → **一条大导出堵住整条队列** | prefetch 可配（3~5）+ 可横向多 worker |
| 生成方式 | 反序列化整份数据 + PHPExcel **全内存** | **游标分片查询 + 流式写文件**（大导出默认 CSV） |
| 失败处理 | 任何异常无限 requeue（超 3 次收走标记失败） | **失败分类**：参数类直接失败、抖动类退避重试、超限入死信 |
| 交付体验 | HTTP 里等结果 / 事后到"导出记录"翻 | **任务中心**：进度可查、文件可下载、完成后通知 |
| 隔离 | 所有导出共用一条 `export_queue` | 按业务/轻重拆队列，超大导出独立 worker |

**投入最小、见效最快的两件事**：① 消费者 prefetch 可配 + 多开 worker；② 请求侧加"行数上限 + 频率限制"。
**治本的一件事**：`sendToExport($list)` → `sendToExportJob($params)`（62 处调用点分批替换）。

## 2. 根因分析（为什么会"堵队列"）

1. **消息体里装数据**：一份几万行的导出 JSON 可达几十 MB。RabbitMQ 单消息受 `max_message_size`（默认 128MB）约束，大消息占 Broker 内存、持久化写盘慢，易触发 flow control；**一条大消息本身就等于把队列卡住**。
2. **prefetch=1 + 单消费者**：`basic_qos(0,1,false)` 表示"上一条没处理完不再收下一条"。一条 10 分钟的大导出 = 队列后面所有小导出手动排队 10 分钟。
3. **消费端全内存**：`json2arr()` 反序列化整份数据 + PHPExcel 全量内存模型 → 内存峰值高、耗时长 → 超时/异常 → `nack(requeue)` → **同一条消息反复重投**，把队列刷爆（`export_max_redeliver=3` 只是兜底止血）。
4. **请求侧同步查全量**：HTTP 内 `select` 全量（含大 join、深分页 `LIMIT offset,n`）→ 接口慢、占 DB 连接，用户体感"点了没反应"。
5. **失败不分类**：参数/权限类错误也走 requeue，白耗重投配额后才标记失败，用户只看到"失败"。
6. **无隔离、无背压**：订单/商品/营收导出共用一条队列；队列深度无监控、无拒绝策略。

## 3. 总体设计

```
                        ┌─────────────────────────────────────────────┐
  HTTP 导出接口(62处)     │ ① 鉴权 + 条件校验 + 行数/频率护栏            │
                        │ ② 写 export_log(status=1, job_type, params)  │
                        │ ③ 入队 {export_id, job_type, params}         │  ← 消息恒定 ≤ 1KB
                        │ ④ 立即返回"已提交，请到导出中心下载"          │
                        └───────────────────┬─────────────────────────┘
                                            ▼
                       export_queue（prefetch 可配 3~5，可多 worker 横向扩）
                                            ▼
                        ┌─────────────────────────────────────────────┐
  Worker                │ ⑤ 置 status=2（幂等：已完成直接 ack）         │
                        │ ⑥ 游标分片查询 WHERE id > :last ORDER BY id  │
                        │    LIMIT n（每批 1000~5000，走只读从库）      │
                        │ ⑦ 流式写文件（CSV fputcsv / xlsx 分片）       │
                        │ ⑧ 回写 progress / row_count / file_path      │
                        └───────────────────┬─────────────────────────┘
                                            ▼
              文件存储（本地/OSS，带 expire_time）→ 任务中心（进度/下载/重试/删除）
                                            ▼
                              完成通知（站内信）／失败留 fail_reason
```

**设计原则**

| 原则 | 说明 |
|---|---|
| 消息只传 ID/条件 | 消息体与数据量**解耦**，MQ 只承担"任务调度"，不承担"数据搬运" |
| 查询分片 + 写入流式 | 内存峰值与总行数解耦，几十万行也能稳定跑 |
| 幂等 + 状态机 | `export_id` 为幂等键，重复投递不重复生成、不重复占资源 |
| 失败分类 | 不可重试错误快速失败并留原因；可重试错误退避重试；超限入死信 |
| 隔离与背压 | 队列按业务/轻重拆分；队列深度超阈值拒绝新任务并明确提示 |
| 兼容灰度 | 新旧消息同队列并行，按"是否含 `list`"分流，可随时回滚 |

## 5. 数据结构变更（DDL 草案）

```sql
-- export_log：从"记录"升级为"任务"
ALTER TABLE `export_log`
  ADD COLUMN `job_type` varchar(50) NOT NULL DEFAULT '' COMMENT '任务类型' AFTER `export_position`,
  ADD COLUMN `params` text COMMENT '入队参数快照(JSON)' AFTER `job_type`,
  ADD COLUMN `progress` tinyint unsigned NOT NULL DEFAULT 0 COMMENT '进度百分比' AFTER `status`,
  ADD COLUMN `row_count` int unsigned NOT NULL DEFAULT 0 COMMENT '导出行数' AFTER `progress`,
  ADD COLUMN `file_size` bigint unsigned NOT NULL DEFAULT 0 COMMENT '文件字节数' AFTER `file_path`,
  ADD COLUMN `fail_reason` varchar(255) NOT NULL DEFAULT '' COMMENT '失败原因' AFTER `file_size`,
  ADD COLUMN `worker_id` varchar(64) NOT NULL DEFAULT '' COMMENT '执行worker标识' AFTER `fail_reason`,
  ADD COLUMN `expire_time` int unsigned NOT NULL DEFAULT 0 COMMENT '文件过期时间(秒级时间戳)' AFTER `worker_id`;
```

**状态语义与兼容**（二选一，推荐先做①）：

| 方案 | 做法 | 影响 |
|---|---|---|
| ① 保持 `status` 三值语义（1 排队 / 2 完成 / 4 失败） | 新增 `progress`、`row_count`、`fail_reason` 等，用 `progress=100 且 file_path 非空` 表示完成 | **老前端零改动**，改动最小 |
| ② 全状态机（1 排队 / 2 处理中 / 3 完成 / 4 失败 / 5 过期） | 需同步改前端列表渲染，并把历史 `status=2` 重刷为 `3` | 语义更清晰，但有前端联动成本 |

> 无论选哪种，`export_id` 都是**幂等键**：消费端先"抢状态"（`update ... where status=1`），抢不到即视为已被处理。

## 6. 消息协议变更

### 6.1 旧（携带数据，现状 62 处）

```json
{
  "export_id": 10231,
  "filename": "订单导出",
  "title": ["订单号", "金额", "..."],
  "list": [ [1, "..."], [2, "..."] ],
  "otherData": { "startRow": 1, "merge": [] }
}
```

### 6.2 新（只传条件，目标形态）

```json
{
  "export_id": 10231,
  "filename": "订单导出",
  "job_type": "sale_orders_export",
  "params": {
    "where": { "ao_id": 17, "start_time": 1757000000, "end_time": 1757600000 },
    "order": "order_id desc",
    "currency_code": "CNY",
    "has_cost_price_auth": 1
  },
  "otherData": { "startRow": 1 }
}
```

**改造约定**

1. `params` 必须是**可序列化的查询条件**（不含 HTML、文件流、大数组）；
2. 导出的**表头/列**由消费端按 `job_type` 决定，前端只传条件（避免把 `title` 塞进消息）；
3. 多 Sheet/汇总场景用 `sheets: [{job_type, params, sheetName}]`，同样**不携带数据**；
4. 消息体大小上限建议在入队处断言（如 `strlen($msg) > 8192` 直接拒绝入队并告警，防止"又退回老路"）。

## 7. 关键实现要点

### 7.1 游标分片查询（避免深分页）

```php
$lastId = 0; $batch = 2000; $setCount = 0;
while (true) {
    $rows = Db::name('sale_orders')->alias('a')/* ->join(...) 与主列表同口径 */
        ->where($where)
        ->where('a.order_id', '>', $lastId)          // ← keyset 分页，禁止 LIMIT offset,n
        ->order('a.order_id', 'asc')                  // ← 固定排序键（主键最优）
        ->limit($batch)
        ->select()->toArray();
    if (!$rows) break;
    foreach ($rows as $row) {
        fputcsv($fh, $this->formatRow($row));         // ← 逐行写，不累积数组
        $lastId = intval($row['order_id']);
        $setCount++;
    }
    if (($setCount % 10000) === 0) {                  // ← 不要每行 update
        $this->updateExportLog(['export_id' => $id, 'row_count' => $setCount, 'progress' => 30]);
    }
    usleep(20000);                                     // ← 让出资源，避免打满 DB/IO
}
```

**必须注意**：导出期间数据可能变化 → 固定排序键 + 固定条件快照；必要时叠加"导出开始时间"过滤，保证不重不漏。

### 7.2 流式写文件

| 格式 | 方案 | 适用 |
|---|---|---|
| CSV | `fopen()` + `fputcsv()` 逐行写 | **默认**，几十万行无压力 |
| XLSX | 分批写 + 每批 `gc_collect_cycles()` | ≤5 万行 |
| 超大 XLSX | 分片生成多文件后 zip | 必须 xlsx 的超大数据 |

先写 `xxx.tmp`，全部写完再 `rename()` 为最终文件，避免"半成品被下载"。

### 7.3 幂等与状态抢占

```php
$status = (int)Db::name('export_log')->where('export_id', $id)->value('status');
if ($status === 2) { $message->ack(); return; }                // 已完成：直接 ack（沿用现有逻辑）

$affected = Db::name('export_log')
    ->where(['export_id' => $id, 'status' => 1])                // 抢占式更新
    ->update(['status' => 2, 'worker_id' => $workerId, 'update_time' => time()]);
if (!$affected) { $message->ack(); return; }                    // 已被其他 worker 抢到 → 丢弃，避免重复生成
```

### 7.4 失败分类

| 异常类型 | 处理策略 |
|---|---|
| 参数非法 / 无权限 / 行数超限 / 格式不支持 | `status=4` + `fail_reason`，**不重投**（避免白耗重投配额） |
| DB 抖动 / IO 忙 / 锁等待 | `nack(requeue)` + 计数，超 `export_max_redeliver` → 死信队列 + `status=4` |
| 进程被杀 / OOM | 依赖 MQ 重投 + §7.3 的状态抢占保证不重复生成 |

### 7.5 背压与护栏

- 队列深度 > 阈值（如 200）→ 新任务直接返回"当前导出任务较多，请稍后重试"；
- 单用户同时进行中任务 ≤ 3，同接口 60s 限一次；
- 导出接口**必须**有收敛条件（时间范围 / `ao_id` / `m_id` 等），禁止无条件全表导出。

### 7.6 校验清单（改造自检）

- [ ] 消息体**不含** `list`/`sheets.*.list`（可用守卫静态断言）
- [ ] 查询走 keyset 分页且排序键固定
- [ ] 写文件为流式，内存不随行数增长
- [ ] `export_log` 有进度/行数/文件路径/失败原因
- [ ] 重复投递不重复生成文件（状态抢占生效）
- [ ] 失败分类：参数类不重投
- [ ] 导出查询走从库（如已提供）

## 8. 风险、兼容与回滚

| 风险 | 缓解 |
|---|---|
| 新旧消息格式混跑 | 消费端按"含 `list` → 老逻辑"分流；灰度逐个接口切换，可随时回滚到旧入队 |
| `export_log.status` 语义扩展影响老前端 | 采用 §5 方案①（保持 1/2/4 三值），前端零改动 |
| prefetch 提高后内存上升 | P1 完成后消息才变小；P0 阶段先设 2~3，并显式设置 `memory_limit` |
| 分片导出期间数据变动 | 固定排序 + 条件快照 + 可选的"导出开始时间"过滤 |
| 从库延迟导致导出偏旧 | 业务上可接受；如必须实时，提供"小范围直查"通道 |
| 导出文件堆积占空间 | `expire_time` + 定时清理任务 |
| 改造面大（62 处） | 按接口分批 + 新旧并行 + 守卫防回归；优先改"行数最大"的接口 |

**回滚方式**：新入队方法仅新增分支，回滚只需把调用点换回 `sendToExport($list)`（或保留开关 `config('export.use_job_mode')` 控制）。

## 9. 落地计划与验收

| 批次 | 内容 | 预估 | 验收标准 |
|---|---|---|---|
| P0 | prefetch 可配 + 多 worker + 护栏 + 失败分类 | 1~2 天 | 小导出不再被大导出阻塞；参数错误不重投 |
| P1 | Job 化入队（62 处分批）+ 分片流式生成 | 3~5 天（按接口分批） | 20 万行导出：消息 < 1KB、worker 内存 < 200MB、期间其他导出正常 |
| P2 | 任务中心 + 存储 + 通知 + 前端改造 | 约 1 周 | 提交后可在导出中心看到进度并下载；完成后收到通知 |
| P3 | 拆队列 + 轻重分级 + 超大导出 + 监控 | 按需 | 队列深度/耗时/失败率可观测并告警 |

**每批完成后补守卫**（遵循仓库 `tests/*_guard.php` 惯例）：

1. 静态守卫：导出入队构造处**不得**出现 `'list' =>`（兼容分支除外）；
2. 静态守卫：`MqConsumer` 的 prefetch 读配置、失败分类分支存在；
3. 静态守卫：`ExportClient` 每个 `job_type` 都有分片查询 + 流式写实现；
4. 静态守卫：`export_log` 任务字段齐全（progress/row_count/fail_reason/expire_time）。
