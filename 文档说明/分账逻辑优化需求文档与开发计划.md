# 分账逻辑优化需求文档与开发计划

## 1. 背景

当前系统已有收款策略、分润策略、策略绑定设备、策略绑定账号、订单分账记录等能力：

- `strategy_payee`：收款策略，记录支付渠道配置。
- `strategy_income`：分润策略，当前主要记录分润比例、转账方式。
- `strategy_machine`：策略绑定设备，`s_type=1` 表示收款策略，`s_type=3` 表示分润策略。
- `strategy_manager`：策略绑定账号，当前用于把策略和管理员账号关联。
- `sale_orders_revenue`：订单分账记录，支付前生成，支付成功后结算。
- `auth_org_revenue_logs`：组织分账日志，当前用于组织租赁分账记录。

现有分账入口在 `BeforeOrderPaymentTrait::countIncome()`，结算入口在 `AfterOrderPaymentTrait::settlementRevenue()`。现有逻辑已经尝试支持“子订单组织与父订单组织不同”的租赁分账，但模型不够清晰，且策略、分账账户、账户管理人的关系分散在不同表中，后续扩展普通分账、设备出租、设备固定比例分账时容易冲突。

## 2. 业务目标

1. 配置收款策略时，必须同时配置分账账户及账户管理人。
2. 支持三类分账模式：
   - 普通分账模式：设备上只有组织 A 的商品，设备订单分账归属于组织 A。
   - 设备出租模式：A 组织设备销售 B 组织商品，收款方为 A；当 B 组织商品发生交易时，A 作为代收方，应给 B 组织分账，分账金额为该商品交易金额。
   - 设备分账模式：设备预先绑定一组分账策略，如 B 组织 20%、C 组织 30%；设备产生订单且收款方为 A 时，按策略给 B、C 分账。
3. 上述所有场景产生的分账订单，都必须能在对应账户管理人后台查询到。
4. 分账记录需要可追踪到订单、子订单、设备、收款策略、分账模式、分账账户、账户管理人、收款组织和受益组织。

## 3. 范围

### 3.1 本期纳入

- 优化分账数据模型。
- 明确收款策略、分账账户、账户管理人之间的配置关系。
- 重构订单分账生成规则，统一三种场景。
- 完善账户管理人后台分账订单查询口径。
- 提供历史数据兼容和迁移方案。

### 3.2 本期暂不纳入

- 第三方支付平台真实分账接口改造。
- 自动提现、自动打款、财务对账。
- 历史订单重新计算分账金额。

## 4. 名词定义

- 收款组织：订单实际收款方所属组织，通常来自设备组织或收款策略所属组织。
- 商品组织：订单明细商品归属组织，来自 `sale_orders_details.sod_ao_id`。
- 分账接收组织：最终获得分账金额的组织。
- 分账账户：接收分账的资金账户，可关联管理员账号余额、银行卡、支付宝、微信、京东分账账户等。
- 账户管理人：可查看并管理某个分账账户及其分账订单的后台管理员。
- 分账模式：决定分账接收方和金额计算方式的业务规则。

## 5. 当前逻辑问题

1. 收款策略只记录支付配置，未强约束分账账户及账户管理人。
2. `strategy_income` 只能表示单个比例策略，无法表达“策略组”和多个接收组织的关系。
3. `strategy_manager` 同时承载策略账号绑定、提现权限等含义，语义混杂。
4. 设备出租分账依赖子订单组织字段，但代码中使用 `sod_ao_id`，数据库更新脚本中也出现过 `ao_id` 字段，需统一字段口径。
5. `sale_orders_revenue` 缺少明确的分账模式、收款组织、接收组织、账户管理人快照字段。
6. `auth_org_revenue_logs` 和 `sale_orders_revenue` 存在重叠，容易产生双份查询口径。

## 6. 推荐设计

### 6.1 设计原则

- 订单分账只生成一套权威明细：以 `sale_orders_revenue` 为准。
- 分账策略配置和订单分账结果分离。
- 订单分账结果保存快照，后续策略修改不影响历史订单。
- 后台查询按账户管理人授权过滤，而不是只按登录人组织过滤。
- 兼容现有表，优先扩展字段；复杂关系使用新表。

### 6.2 新增分账账户表

建议新增 `revenue_account`，统一管理组织分账账户及账户管理人。

```sql
CREATE TABLE `revenue_account` (
  `ra_id` int NOT NULL AUTO_INCREMENT COMMENT '分账账户ID',
  `ao_id` int NOT NULL COMMENT '账户所属组织ID',
  `manager_id` int NOT NULL COMMENT '账户管理人ID',
  `account_name` varchar(100) DEFAULT NULL COMMENT '账户名称',
  `account` varchar(255) DEFAULT NULL COMMENT '分账账户',
  `account_type` varchar(50) DEFAULT 'balance' COMMENT '账户类型 balance/bank/alipay/wechat/jd_account',
  `bill_account` varchar(255) DEFAULT NULL COMMENT '兼容旧管理员分账账号',
  `status` tinyint(1) DEFAULT 1 COMMENT '状态：1启用，2停用',
  `creator` int DEFAULT NULL COMMENT '创建人',
  `create_time` int DEFAULT NULL,
  `update_time` int DEFAULT NULL,
  PRIMARY KEY (`ra_id`),
  KEY `idx_ao_manager` (`ao_id`, `manager_id`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分账账户表';
```

### 6.3 收款策略绑定默认分账账户

建议扩展 `strategy_payee`：

```sql
ALTER TABLE `strategy_payee`
  ADD COLUMN `default_ra_id` int DEFAULT NULL COMMENT '默认分账账户ID' AFTER `ao_id`,
  ADD COLUMN `default_manager_id` int DEFAULT NULL COMMENT '默认账户管理人ID' AFTER `default_ra_id`;
```

规则：

- 新增或修改收款策略时，必须传入 `default_ra_id` 或同时传入账户信息创建分账账户。
- `default_ra_id` 所属组织必须等于 `strategy_payee.ao_id`。
- `default_manager_id` 必须等于 `revenue_account.manager_id`，或者由 `default_ra_id` 自动反查。

### 6.4 分账策略组

建议新增策略组主表 `revenue_rule`，用于表示普通分账、设备出租、设备分账三类规则。

```sql
CREATE TABLE `revenue_rule` (
  `rr_id` int NOT NULL AUTO_INCREMENT COMMENT '分账策略组ID',
  `rule_name` varchar(100) NOT NULL COMMENT '策略名称',
  `rule_mode` tinyint(1) NOT NULL COMMENT '模式：1普通分账，2设备出租，3设备分账',
  `payer_ao_id` int DEFAULT NULL COMMENT '收款/代收组织ID',
  `status` tinyint(1) DEFAULT 1 COMMENT '状态：1启用，2停用',
  `creator` int DEFAULT NULL,
  `create_time` int DEFAULT NULL,
  `update_time` int DEFAULT NULL,
  PRIMARY KEY (`rr_id`),
  KEY `idx_mode_status` (`rule_mode`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分账策略组表';
```

新增策略明细表 `revenue_rule_item`：

```sql
CREATE TABLE `revenue_rule_item` (
  `rri_id` int NOT NULL AUTO_INCREMENT COMMENT '分账策略明细ID',
  `rr_id` int NOT NULL COMMENT '分账策略组ID',
  `receiver_ao_id` int NOT NULL COMMENT '分账接收组织ID',
  `ra_id` int NOT NULL COMMENT '分账账户ID',
  `manager_id` int NOT NULL COMMENT '账户管理人ID',
  `calc_type` tinyint(1) DEFAULT 1 COMMENT '计算方式：1百分比，2固定金额，3全额',
  `calc_value` decimal(10,3) DEFAULT 0.000 COMMENT '百分比或固定金额',
  `sort` int DEFAULT 0,
  `status` tinyint(1) DEFAULT 1,
  PRIMARY KEY (`rri_id`),
  KEY `idx_rr_status` (`rr_id`, `status`),
  KEY `idx_receiver` (`receiver_ao_id`),
  KEY `idx_manager` (`manager_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分账策略明细表';
```

### 6.5 设备绑定策略组

建议新增 `revenue_rule_machine`，不要继续复用 `strategy_machine.s_type=3` 表达复杂分账策略。

```sql
CREATE TABLE `revenue_rule_machine` (
  `rrm_id` int NOT NULL AUTO_INCREMENT COMMENT '设备分账策略绑定ID',
  `rr_id` int NOT NULL COMMENT '分账策略组ID',
  `m_id` int NOT NULL COMMENT '设备ID',
  `ao_id` int DEFAULT NULL COMMENT '设备组织ID',
  `sort` int DEFAULT 0,
  `status` tinyint(1) DEFAULT 1,
  `create_time` int DEFAULT NULL,
  `update_time` int DEFAULT NULL,
  PRIMARY KEY (`rrm_id`),
  UNIQUE KEY `uk_machine_rule` (`m_id`, `rr_id`),
  KEY `idx_machine_status` (`m_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='设备分账策略绑定表';
```

### 6.6 扩展订单分账记录

建议扩展 `sale_orders_revenue`，使其成为唯一权威查询表。

```sql
ALTER TABLE `sale_orders_revenue`
  ADD COLUMN `rule_mode` tinyint(1) DEFAULT 0 COMMENT '分账模式：1普通，2设备出租，3设备分账' AFTER `revenue_type`,
  ADD COLUMN `rr_id` int DEFAULT NULL COMMENT '分账策略组ID' AFTER `si_id`,
  ADD COLUMN `rri_id` int DEFAULT NULL COMMENT '分账策略明细ID' AFTER `rr_id`,
  ADD COLUMN `payer_ao_id` int DEFAULT NULL COMMENT '收款/代收组织ID' AFTER `ao_id`,
  ADD COLUMN `receiver_ao_id` int DEFAULT NULL COMMENT '分账接收组织ID' AFTER `payer_ao_id`,
  ADD COLUMN `ra_id` int DEFAULT NULL COMMENT '分账账户ID' AFTER `receiver_ao_id`,
  ADD COLUMN `manager_name` varchar(100) DEFAULT NULL COMMENT '账户管理人名称快照' AFTER `manager_id`,
  ADD COLUMN `account_type` varchar(50) DEFAULT NULL COMMENT '账户类型快照' AFTER `bill_account`,
  ADD COLUMN `account` varchar(255) DEFAULT NULL COMMENT '分账账户快照' AFTER `account_type`,
  ADD COLUMN `source` varchar(50) DEFAULT NULL COMMENT '来源：normal/rental/device_rule/legacy' AFTER `account`,
  ADD KEY `idx_manager_status` (`manager_id`, `status`),
  ADD KEY `idx_receiver_status` (`receiver_ao_id`, `status`),
  ADD KEY `idx_rule_mode` (`rule_mode`);
```

`auth_org_revenue_logs` 后续可作为日志冗余保留，但后台查询与导出建议统一从 `sale_orders_revenue` 查询。

## 7. 分账规则

### 7.1 规则优先级

订单支付前生成分账记录时，按以下顺序判断：

1. 设备出租模式：订单明细商品组织与订单收款组织不同。
2. 设备分账模式：设备绑定了启用状态的 `rule_mode=3` 策略组。
3. 普通分账模式：以上都未命中时，归属于订单收款组织默认分账账户。

说明：同一笔订单可以同时包含设备出租分账和设备分账。若业务要求互斥，建议配置项控制。本需求默认：

- B 组织商品在 A 设备销售时，B 先获得该商品明细全额。
- 设备分账模式按订单可分账基数再分给 B/C。为避免超额，设备分账基数建议使用订单金额扣除出租商品全额后的剩余金额；若业务希望按订单总额计算，需要在策略组增加 `base_type` 字段。

### 7.2 普通分账模式

适用条件：

- 设备上只有组织 A 商品，或订单明细商品组织均等于订单收款组织。
- 未绑定设备分账策略。

生成规则：

- `payer_ao_id = order.ao_id`
- `receiver_ao_id = order.ao_id`
- `ra_id = strategy_payee.default_ra_id`
- `manager_id = revenue_account.manager_id`
- `income_amount = order.total_price`
- 若按明细生成，则每条明细按 `sod_total_price` 生成一条。
- `rule_mode = 1`
- `source = normal`

### 7.3 设备出租模式

适用条件：

- 订单收款组织为 A。
- 子订单商品组织为 B，且 B 不等于 A。

生成规则：

- 按子订单明细生成。
- `payer_ao_id = order.ao_id`
- `receiver_ao_id = sale_orders_details.sod_ao_id`
- `income_amount = sale_orders_details.total_sod_price`
- `calc_type = 3`，等价全额分账。
- `rule_mode = 2`
- `source = rental`

账户获取：

- 优先使用 B 组织绑定的默认分账账户。
- 如果 B 组织未配置分账账户，则订单支付前应返回错误，不允许继续支付，避免代收后无法追踪。

### 7.4 设备分账模式

适用条件：

- 设备绑定启用状态 `rule_mode=3` 的策略组。
- 策略组中存在启用状态的策略明细。

生成规则：

- `payer_ao_id = order.ao_id`
- 按策略明细生成多条分账记录。
- 例如 B 20%、C 30%：
  - B：`income_amount = base_amount * 20%`
  - C：`income_amount = base_amount * 30%`
- `receiver_ao_id`、`ra_id`、`manager_id` 来自 `revenue_rule_item`。
- `rule_mode = 3`
- `source = device_rule`

校验：

- 同一个策略组内百分比合计不能超过 100%。
- 每个接收组织必须配置有效分账账户和账户管理人。
- 金额低于 0.01 的记录不生成。

## 8. 后台查询需求

### 8.1 账户管理人后台分账订单列表

新增或改造接口：

- `GET /management/revenue.order/getList`

查询条件：

- 订单号、设备编号、设备名称。
- 分账模式：普通、设备出租、设备分账。
- 分账状态。
- 收款组织、接收组织。
- 时间范围。
- 账户管理人。

权限规则：

- 超级管理员或具备分账审核权限账号可查看授权范围内全部分账订单。
- 普通账户管理人只能查看 `sale_orders_revenue.manager_id = 当前登录manager_id` 的记录。
- 组织管理员可查看本组织作为收款组织或接收组织的记录，具体以角色权限配置为准。

列表字段：

- 分账单 ID：`sor_id`
- 订单 ID、订单号、子订单 ID。
- 设备 ID、设备编号、设备名称。
- 收款组织、接收组织。
- 分账模式、分账来源。
- 订单金额、子订单金额、分账比例、分账金额、退款金额、可结算金额。
- 分账账户、账户类型、账户管理人。
- 分账状态、创建时间、结算时间。

### 8.2 分账详情

新增或改造接口：

- `GET /management/revenue.order/getFind`

详情需展示：

- 订单基础信息。
- 支付信息：收款策略、支付类型、收款方。
- 商品明细。
- 分账明细。
- 退款关联记录。

### 8.3 分账策略配置后台

新增或改造模块：

- 分账账户管理：新增、修改、停用、绑定账户管理人。
- 分账策略组管理：普通、设备出租、设备分账策略配置。
- 设备绑定策略：给设备绑定设备分账策略组。
- 收款策略配置：强制选择默认分账账户。

## 9. 数据兼容与迁移

1. 保留现有 `strategy_income`、`strategy_machine.s_type=3`、`strategy_manager` 逻辑，短期内作为 legacy 兼容。
2. 新增分账账户时，可从 `auth_manager.bill_account` 初始化：
   - `ao_id = auth_manager.ao_id`
   - `manager_id = auth_manager.manager_id`
   - `account_type = balance`
   - `bill_account = auth_manager.bill_account`
3. 已有收款策略按 `strategy_payee.ao_id` 反查同组织默认分账账户，补齐 `default_ra_id`。
4. 已有分账记录补齐：
   - `rule_mode = 0`
   - `source = legacy`
   - `receiver_ao_id = ao_id`
   - `payer_ao_id` 尽量从订单 `sale_orders.ao_id` 回填。
5. 统一订单明细组织字段：
   - 代码当前主要使用 `sod_ao_id`。
   - 如果数据库实际存在 `ao_id`，需迁移或增加兼容读取。
   - 推荐最终统一使用 `sod_ao_id`，避免和订单主表 `ao_id` 混淆。

## 10. 验收标准

1. 新建收款策略时，未配置分账账户及账户管理人，不允许保存。
2. 普通分账模式订单支付前能生成归属于组织 A 的分账记录。
3. 设备出租模式下，A 设备销售 B 商品时，B 能获得该商品明细全额分账记录。
4. 设备分账模式下，设备绑定 B 20%、C 30% 策略后，订单支付前生成对应比例的分账记录。
5. 支付成功后，分账记录状态能按现有结算流程更新。
6. 账户管理人登录后台，只能查询到自己管理账户对应的分账订单。
7. 退款后，分账记录能正确体现退款金额和可结算金额。
8. 历史分账记录不丢失，旧接口在兼容期内可正常查询。

## 11. 开发计划

### 阶段一：需求确认与表结构落地

预计 1-2 天。

- 确认设备出租和设备分账是否允许同一订单同时生效。
- 确认设备分账计算基数：订单总额、扣除出租商品后的金额，或按商品范围。
- 确认分账账户类型和提现/余额结算关系。
- 新增 `revenue_account`、`revenue_rule`、`revenue_rule_item`、`revenue_rule_machine`。
- 扩展 `strategy_payee`、`sale_orders_revenue`。
- 修复或兼容 `sale_orders_details.sod_ao_id` 字段口径。

### 阶段二：管理后台配置接口

预计 2-3 天。

- 新增分账账户管理接口。
- 改造收款策略新增/修改校验，强制绑定默认分账账户。
- 新增分账策略组接口。
- 新增设备绑定分账策略接口。
- 增加配置校验：账户有效、管理人有效、组织匹配、比例不超过 100%。

### 阶段三：订单分账生成服务

预计 2-4 天。

- 抽离统一分账计算服务，例如 `RevenueCalculator`。
- 重构 `BeforeOrderPaymentTrait::countIncome()`：
  - 识别普通分账。
  - 识别设备出租分账。
  - 识别设备分账策略。
  - 生成统一 `sale_orders_revenue` 记录。
- 保留 legacy 逻辑作为兜底，并加日志标记。
- 对支付发起、终端活动订单、API V2 下单等入口统一调用。

### 阶段四：结算与退款兼容

预计 1-2 天。

- 改造 `settlementRevenue()`，按 `ra_id/manager_id/account_type` 结算。
- 保留当前电子钱包余额增加逻辑。
- 校验退款流程对 `refund_amount`、`refund_status` 的影响。
- 确保幂等：已结算分账不重复入账。

## 12. 风险与待确认问题

1. 设备出租和设备分账同时存在时，是否都要执行，还是设备出租优先并排除设备分账。    
2. 设备分账的计算基数是否为订单总额。
3. 普通分账是否需要生成 `sale_orders_revenue` 记录；本方案建议生成，便于账户管理人统一查询。
4. 账户管理人是否可以管理多个组织的分账账户。
5. `auth_org_revenue_logs` 是否继续保留为业务日志，还是迁移后废弃。
6. 现网数据库中 `sale_orders_details` 组织字段实际名称需要确认，建议统一为 `sod_ao_id`。
