# 设备商品库存变化统计接口设计方案

> 版本：v1.0 ｜ 适用分支：`uat` / `main_fix_stock` ｜ 适用库：`kiosk`
> 目标：按 `m_id + g_id + 起止时间` 输出「初始库存 / 累计上架 / 累计下架 / 累计销售 / 剩余库存」，
> 满足 `初始库存 + 累计上架 = 累计下架 + 累计销售 + 剩余库存`；
> 并为累计上架/下架/销售各提供**明细接口**，关联补货单、库存流水日志与订单，做到**有据可查**。

---

## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| 接口数量 | 1 个主统计 + 3 个明细（上架/下架/销售） |
| 库存口径 | **以 `machine_channel` 货道库存汇总为准**（`machine_goods` 上的同名列是历史遗留、恒为 0） |
| 上架/下架来源 | `machine_channel_replenishment`（补货单 `quantity` 正负），明细附**同刻库存流水** `goods_change` |
| 销售来源 | `sale_orders_details.success_quantity`（`pay_status=3` 且 `out_status in (4,6)`，时间取 `out_time`），明细带订单号 |
| 初始库存 | 系统**无历史库存快照表**，只能由「实物锚点 − 台账」反推；因此额外返回**四方对账差额**暴露数据缺口 |
| 等式 | `equation.diff = 0` 且 `balanced = true`（当前实现为构造保证，差额区块用于发现台账缺失） |

## 2. 口径定义（含选型依据）

| 项 | 取值 | 依据 / 代码位置 |
|---|---|---|
| 剩余库存（期末） | `Σ machine_channel.stock`（`status=1` 记 available、`status>1` 记 disabled），另附 `frozen_stock` 预定与 `machine_goods.standby_stock` 备用 | `MachineGoodsModel::STOCK_FIELDS` 注释明确"machine_goods 同名列属历史遗留且不再维护（恒为 0），真实库存以 machine_channel 货道库存汇总为准" |
| 累计上架 | `Σ machine_channel_replenishment.quantity`（`quantity > 0`） | 补货单含 `before/after/rep_type/creator`，天然可溯源 |
| 累计下架 | `Σ |quantity|`（`quantity < 0`） | 同上；**含"退回备用库存"**（库存离开货道即计下架，备用区单独展示） |
| 累计销售 | `Σ sale_orders_details.success_quantity`，条件 `o.pay_status=3 AND o.out_status IN (4,6)`，时间取 `o.out_time` | 实测该组合 1922/1922 条 `success_quantity` 与 `quantity` 一致，是最干净的"已支付且已出货"集合 |
| 上架/下架时间字段 | `machine_channel_replenishment.create_time` | 与 `goods_change.create_time` 同事务写入，可直接对拍 |
| 销售时间字段 | `sale_orders.out_time` | `sale_orders_details` 无时间字段，出货时间才代表库存真实减少 |
| 流水分类（交叉核对用） | 上架类 `goods_change.type ∈ {2,4,6,9,11}`；下架类 `∈ {3,5,7,8,10}`；历史销售类 `{1}` | 由写入点归纳；**注意**：出货成功写的是 `type=3`（与下架同类型，见 `OutGoodsTrait:311-314`），故流水无法独立区分销售，销售一律以订单为准 |

## 3. 取值逻辑与等式

```
锚点 A_now  = 货道库存汇总（实物锚点，与设备商品列表同口径）
期末 C(t1)  = A_now                                     （t1 = now）
            = A_now − Σ_{t1..now}(上架 − 下架 − 销售)      （t1 < now，台账回推，closing_source=derived_from_anchor）
台账 L(t0,t1) = { 上架 U, 下架 D, 销售 S }
初始库存 O(t0) = C(t1) − (U − D − S)
等式：O + U = D + S + C(t1)   恒成立（equation.diff = 0，balanced = true）
```

**为什么期初是"反推"**：系统没有按日快照的库存表，任何"期初"都只能由期末锚点加减台账得到，
因此等式本身**是构造保证**；真正有对账价值的是 `cross_check`（见 §4）——差额≠0 即说明台账缺失或口径不一致。

## 4. 对账区块（`cross_check`）与实测暴露的问题

| 字段 | 含义 | 实测（m_id=127, g_id=1001，近 90 天） |
|---|---|---|
| `shelved_doc` / `shelved_log` | 上架：补货单 vs 流水 | 13 vs **5211**（差额 −5198） |
| `unshelved_doc` / `unshelved_log` | 下架：补货单 vs 流水 | 6 vs **3439**（差额 −3433） |
| `sold_order` / `sold_log` | 销售：订单 vs 流水 | 206 vs **0**（销售未落 `goods_change`，`type=1` 近 90 天 0 条） |
| `stock_anchor` / `stock_by_ledger` | 实物锚点 vs 台账重算 | 9 vs 9（差额 0） |
| `goods_change_untimed` | 无 `create_time` 的流水条数（无法按区间归属） | **205**（全库 748 条） |

**结论（数据现状，需要治理）**

1. `goods_change` 与补货单**不是一一对应**：流水量级远大于补货单（含换货/BAD/回收/预补货多写）；
2. **销售不写库存流水**：出货成功写的是 `type=3`，且现网几乎未落（`sold_log=0`）→ 销售只能靠订单统计；
3. **748 条流水无时间**：无法归属到任何区间，只能计数提示；
4. `quantity<0` 的补货单包含"退回备用库存"（实测流水 `position=2`、`desc=终端换货-设备商品库上货备用库存`）；
5. `machine_goods` 上的 `available_stock/disabled_stock/reserve_stock` **恒为 0**，不可作为库存来源。

> 因此接口**不隐藏差额**：等式自洽的同时，把"单据/流水/订单/实物"四方差异全部返回，供运营对账与数据治理。

## 5. 实现落点

| 层 | 文件 | 说明 |
|---|---|---|
| 取数 / 口径 | `app/AppFactory/Kernel/Traits/Machine/MachineGoodsStockChangeTrait.php` | 口径静态属性（PHP 7.4 不支持 trait 常量）、库存锚点、台账汇总、流水汇总、主统计、三类明细 |
| 业务 / 权限 | `app/AppFactory/Management/Machine/MachineGoodsClient.php` | 4 个对外方法 + `assertStockChangeMachineScope`（主账号按 `ao_id`、子账号按授权设备，与库存报表口径一致） |
| 控制器 | `app/management/controller/machine/MachineGoods.php` | 4 个方法 + 场景校验接线 |
| 校验器 | `app/management/validate/Machine/VMachineGoods.php` | 新增 `stockChangeStats` / `stockChangeDetail` 场景（`m_id`、`g_id`、`start_time`、`end_time`） |
| 守卫 | `tests/machine_goods_stock_change_guard.php` | 10 项静态断言（口径、等式字段、对账字段、溯源字段、范围校验、接线） |

**权限与数据范围**：所有对外方法先执行 `assertStockChangeMachineScope($m_id)`：
设备不存在 → `VMachine.machine_no_data`；主账号 `ao_id` 不匹配 → `无权查看该设备的库存数据`；子账号未授权该设备 → 同上。

**分页**：明细统一 `pageNum`（从 1 起）/ `pageSize`（≤200），返回 `total` 与区间合计（`sum_quantity` / `sum_success_quantity`）。

## 7. 已知限制与治理建议（后续迭代）

### 7.1 建议新增库存快照表（让"期初/期末"成为独立物理事实）

```sql
CREATE TABLE IF NOT EXISTS `machine_goods_stock_snapshot` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `stat_date` int unsigned NOT NULL COMMENT '统计日期(yyyymmdd)',
  `m_id` int NOT NULL COMMENT '设备ID',
  `g_id` int NOT NULL COMMENT '商品ID',
  `mg_id` int NOT NULL DEFAULT 0 COMMENT '设备商品ID',
  `available_stock` int NOT NULL DEFAULT 0 COMMENT 'status=1 货道库存合计',
  `disabled_stock` int NOT NULL DEFAULT 0 COMMENT 'status>1 货道库存合计',
  `reserve_stock` int NOT NULL DEFAULT 0 COMMENT 'frozen_stock 合计',
  `standby_stock` int NOT NULL DEFAULT 0 COMMENT '备用库存',
  `total_stock` int NOT NULL DEFAULT 0 COMMENT '全部货道库存合计',
  `create_time` int NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_date_device_goods` (`stat_date`,`m_id`,`g_id`),
  KEY `idx_m_g_date` (`m_id`,`g_id`,`stat_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='设备商品日终库存快照（用于期初/期末与对账）';
```

* 定时任务（参考 `app/AppFactory/TimeTask/*`）每日 00:10 写入快照；
* 有快照后：`opening_stock` 直接取 `stat_date = start 当日` 的快照、`closing_stock` 取 `end 当日`，等式差额即成为**真正的对账指标**；
* 接口预留 `closing_source` 字段（`anchor_now` / `derived_from_anchor` / 后续 `snapshot`）。

### 7.2 建议补齐库存流水字段（让销售/下架可区分）

```sql
ALTER TABLE `goods_change`
  ADD COLUMN `biz_type` varchar(32) NOT NULL DEFAULT '' COMMENT '业务来源：sale/unshelf/exchange/bad/recycle/replenish/check' AFTER `type`,
  ADD COLUMN `trade_no` varchar(64) NOT NULL DEFAULT '' COMMENT '关联订单号(销售)/单据号(补货、下架)' AFTER `biz_type`,
  ADD COLUMN `position_stock` int NOT NULL DEFAULT 0 COMMENT '变化后库存快照，便于逐条对账' AFTER `change_value`;
```

* 主要在 `OutGoodsTrait`（出货成功/失败）、`MachineChannelTrait`、`ApiClient`（换货/预补货/回收）、`MachineTrait`（远程下架）等写入点补 `biz_type`/`trade_no`；
* 补齐后：`下架 = Σ(biz_type=unshelf)`、`销售 = Σ(biz_type=sale)`，无需再用订单/单据"间接推断"，明细可直接关联订单号；
* 同时修复 **748 条 `create_time` 为空的流水**（能按 `change_id` 邻近记录推断的批量回填，无法推断的标记为"时间未知"）。

### 7.3 其他

| 限制 | 说明 |
|---|---|
| 销售口径未计"未取商品回收" | 现按 `out_status in (4,6)` 计入成功；`out_status=6`（未取）是否计销售需业务确认 |
| `success_quantity=0` 的历史订单 | 全库 3301 条"已支付+出货成功但 `success_quantity=0`"，会低估历史销售；建议回填（可用 `quantity`） |
| 换货场景 | 换货会产生"新商品上架 + 旧商品下架"，本期按商品维度自然拆分；跨商品迁移不做特殊处理 |
| 多商品货道（`channel_goods_batch`） | 本期按 `machine_channel.g_id` 汇总，批次维度（`batch_id`）统计未纳入 |

## 8. 验收标准

1. `getStockChangeStats` 对任意 `(m_id, g_id, 区间)` 均返回 `equation.balanced = true`；
2. 三类明细的 `total` 与主统计的 `shelved_total` / `unshelved_total` / `sold_total` **逐项可核对**（明细求和 = 主统计值）；
3. 上架/下架明细每行带补货单字段（`before/after/rep_type/creator`）与同刻库存流水（`change_id/type/desc`）；销售明细每行带 `trade_no`、`sod_id`；
4. 越权访问（跨 `ao_id`、未授权子账号）返回 100 且不泄露数据；
5. `start_time/end_time` 必填、倒置拒绝、纯日期结束时间补 `23:59:59`；
6. 守卫 `tests/machine_goods_stock_change_guard.php` 全过。
