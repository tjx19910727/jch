# 故障固定微信模板、上报与后台配置流程

## 1. 最终模板范围

新故障通知只允许以下三个固定模板。模板类型、模板ID和字段协议配置在`config/fault_notice.php`，后台不能新增、删除或修改模板正文。

| template_type | 后台下拉显示 | 微信模板编号 | 适用场景 |
|---|---|---:|---|
| `mFault` | 设备异常提醒（通用模板） | 43033 | 除离线、出货失败外的全部故障 |
| `mOffline` | 售货机离线通知 | 52646 | 持续离线故障 |
| `mShipmentFailed` | 售货机出货失败通知 | 51500 | 出货与取货类故障 |

后台分类只保存`template_type`，不再保存`wx_template.wt_id`。旧`wx_template`表和旧通知流程保留，供非新故障通知业务继续使用。

## 2. 固定字段映射

### 2.1 设备异常提醒（通用模板）

| 微信展示字段 | 微信字段编码 | 数据来源 |
|---|---|---|
| 设备编码 | character_string16 | `machine.machine_id` |
| 设备名称 | thing6 | `machine.machine_name`，最多20字符 |
| 异常现象 | thing12 | 原始故障码`error_code` |
| 异常时间 | time15 | 本次事件创建时间 |
| 设备地址 | thing9 | 故障规则`wechat_text`，即异常现象短名称，最多20字符 |

“设备地址”是微信模板固定字段名称，当前业务不填真实设备地址，固定显示故障短名称。

### 2.2 售货机离线通知

| 微信展示字段 | 微信字段编码 | 数据来源 |
|---|---|---|
| 设备名称 | thing1 | `machine.machine_name` |
| 设备编号 | character_string2 | `machine.machine_id` |
| 最后在线时间 | time4 | `machine.last_online_time` |

### 2.3 售货机出货失败通知

设备上报仍然只包含故障码，不增加订单、商品或货道参数。模板现有字段按以下方式复用：

| 微信展示字段 | 微信字段编码 | 数据来源 |
|---|---|---|
| 设备编号 | character_string1 | `machine.machine_id` |
| 订单编号 | character_string2 | 原始故障码 |
| 商品名称 | thing3 | 故障规则`wechat_text` |
| 出货时间 | time4 | 本次事件创建时间 |
| 货道号 | character_string5 | 固定`-` |

## 3. 分类绑定建议

分类绑定一个模板类型，因此离线必须从原“设备启停与离线”分类中拆出，避免开机、关机故障误用离线模板。

| 故障分类 | template_type | 后台显示 |
|---|---|---|
| 设备离线 | `mOffline` | 售货机离线通知 |
| 出货与取货 | `mShipmentFailed` | 售货机出货失败通知 |
| 设备启停 | `mFault` | 设备异常提醒（通用模板） |
| 通信与网络 | `mFault` | 设备异常提醒（通用模板） |
| 门体与安全 | `mFault` | 设备异常提醒（通用模板） |
| 库存与商品 | `mFault` | 设备异常提醒（通用模板） |
| XY轴运动 | `mFault` | 设备异常提醒（通用模板） |
| Z轴与探头 | `mFault` | 设备异常提醒（通用模板） |
| 气动、电气与传感器 | `mFault` | 设备异常提醒（通用模板） |
| 送料与回收机构 | `mFault` | 设备异常提醒（通用模板） |
| 摄像头与图像 | `mFault` | 设备异常提醒（通用模板） |
| 支付与交易 | `mFault` | 设备异常提醒（通用模板） |
| 打印 | `mFault` | 设备异常提醒（通用模板） |
| 媒体与广告 | `mFault` | 设备异常提醒（通用模板） |

当前没有缺货、关机、柜门和摄像头专用模板进入最终白名单，这些分类统一选择通用模板。

## 4. 后台配置模板流程

### 4.1 获取表单选项

接口：

```text
/management/fault_notice.fault_catalog/getFormOptions
```

`wechat_templates`固定返回三项：

```json
[
  {
    "template_type": "mFault",
    "template_name": "设备异常提醒",
    "display_name": "设备异常提醒（通用模板）",
    "template_no": "43033"
  },
  {
    "template_type": "mOffline",
    "template_name": "售货机离线通知",
    "display_name": "售货机离线通知",
    "template_no": "52646"
  },
  {
    "template_type": "mShipmentFailed",
    "template_name": "售货机出货失败通知",
    "display_name": "售货机出货失败通知",
    "template_no": "51500"
  }
]
```

前端下拉框显示`display_name`，提交`template_type`。

### 4.2 新增分类

```json
{
  "category_name": "出货与取货",
  "template_type": "mShipmentFailed",
  "sort": 50
}
```

后端处理：

1. 校验分类名称和同组织重名。
2. 校验`template_type`必须属于代码白名单且配置完整。
3. `machine_fault_category`只保存`template_type`。
4. 不读取、不保存`wt_id`，也不检查`wx_template`。

### 4.3 编辑分类

```json
{
  "category_id": 5,
  "category_name": "出货与取货",
  "template_type": "mShipmentFailed",
  "sort": 50
}
```

编辑模板类型只影响修改后的新通知，已产生的事件与`wx_template_log`不回写、不补发。

### 4.4 分类列表回显

```json
{
  "category_id": 5,
  "category_name": "出货与取货",
  "template_type": "mShipmentFailed",
  "template_name": "售货机出货失败通知",
  "template_display_name": "售货机出货失败通知",
  "template_status": 1,
  "status": 1
}
```

## 5. 新故障上报流程

### 5.1 入口切换

- HTTP故障上报：`ApiClient::sendErro()`调用`reportFaultCode()`。
- MQ协议保持`msgType=errorCode`不变，`MqClient::onMessage()`在入口映射到`reportFaultCode()`。
- 当前只切换设备主动上报的HTTP、MQ入口。广告为空、设备定时任务、支付异常、商品过期等入口继续使用原流程，后续逐项迁移。
- 旧`MachineErrorCodeTrait::errorCode()`保留，不删除、不修改；入口原调用行改为注释，必要时可以直接切回。

### 5.2 事件落库

1. 校验设备、组织和故障码。
2. 根据`ao_id + error_code`读取`machine_error_code_notice_rule`和分类。
3. 每次上报都新增一条`machine_error_code`，重复上报不合并、不更新计数。
4. 保存事件发生时的`category_id`、`level`快照。
5. 未配置故障码也保存事件，等级默认2，随后标记`notice_status=4`、`notice_reason=error_code_unconfigured`。

事件插入失败才向调用方返回失败。事件插入成功后，即使微信发送异常也不抛给MQ，避免MQ重投导致重复事件或重复通知。

### 5.3 通知策略判断顺序

事件落库后依次判断：

1. 故障码是否已配置。
2. 全局通知总开关。
3. 离线故障通知开关。
4. 分类状态。
5. 故障码状态。
6. 故障码通知开关。
7. 等级静默时段。
8. 同设备、同故障码的通知间隔和每日轮次。
9. 分类`template_type`是否在三个固定模板中且配置完整。
10. 是否存在匹配的通知接收人。

任一步过滤均不调用微信、不写`wx_template_log`、不补发，只更新事件为“未发送”和对应原因。

### 5.4 接收人匹配

接收人必须同时满足：

- 接收配置启用，后台账号启用且已绑定openid和公众号；
- 设备范围为全部设备，或指定设备包含当前`m_id`；
- 子账号仍受`auth_manager_machine`设备权限限制；
- 故障范围为全部故障，或指定分类/故障码命中当前事件。

新流程不读取`auth_manager_notice_config`，也不读取旧`auth_manager.wx_notice`中的`mFault`配置。

### 5.5 模板与发送

1. 从分类取得`template_type`。
2. 从`config/fault_notice.php`取得固定`template_id`和body。
3. 从接收人绑定的`wx_official`取得公众号`app_id/secret`。
4. 根据事件、设备和故障规则生成替换参数。
5. 每个接收人单独调用微信公众号模板消息，只调用WeChat，不调用邮件。
6. 新流程调用`WeChatClient::sendV2()`和`addTemplateLogV2()`；原`send()`和`addTemplateLog()`保持原样，继续服务历史通知流程。
7. 每个实际尝试发送的接收人写一条`wx_template_log`；由于不再使用数据库模板，日志`wt_id=0`，以`template_type/template_id/template_name`识别模板。
8. 汇总事件通知状态：全部成功=1、部分成功=2、全部失败=3、未发送=4。

### 5.6 暂未切换的入口

广告为空、设备未开机/未关机/持续离线定时任务、支付异常、商品过期等继续执行原故障记录或通知逻辑。本轮仅准备`mOffline`等固定模板配置，不改变这些入口；后续迁移时再逐项接入`reportFaultCode()`。

## 6. 后台统计兼容

故障通知不再只有`mFault`，以下查询均按三个模板类型统计：

```text
mFault,mOffline,mShipmentFailed
```

包括：

- 看板通知发送数和成功率；
- 事件列表通知人数、成功数、失败数；
- 故障详情通知记录；
- 等级策略的通知间隔与每日轮次。
