# 分账逻辑当前优化点与影响分析

> 最终实现边界：原收款策略继续使用 `strategy_payee/sp_id`，新分账只允许读取收款结果，不得修改 `strategy_payee` 表结构、数据或保存流程。`revenue_pay_channel` 仅负责渠道开关；普通分账使用 `rule_mode=1`；结算周期归属 `revenue_rule`；`revenue_payee_config` 已删除。本文中与该边界冲突的早期方案均以此说明和《新分账功能变动与影响审计》为准。

## 1. 本次新增口径

### 1.1 设备出租分账支持比例

设备出租场景调整为：

- A 组织设备销售 B 组织商品。
- 订单收款方仍为 A。
- B 组织获得该商品交易金额的一定比例分账。
- 比例后台可配置，允许设置为 100%。

当前实现口径：

- 设备出租分账固定按商品明细全额生成。
- `calc_type=3`
- `income_value=100`
- `income_amount=sale_orders_details.total_sod_price`

需要优化为：

- 设备出租也应进入策略配置体系。
- 对不同商品组织、不同设备、不同收款组织，可配置不同分账比例。
- 100% 只是比例配置的一种特殊情况，不应写死在代码中。

### 1.2 按收款渠道控制是否分账

新增规则：

- 后台可配置“需要分账的收款渠道”。
- 只有订单实际收款渠道在配置范围内，才生成分账订单。
- 未配置为需要分账的收款渠道，即使设备或商品满足分账条件，也不生成 `revenue_order`。

建议口径：

- 收款渠道按 `sale_orders.pay_type` 或确定后的 `strategy_payee.payee_type` 判断。
- 若存在细分渠道，例如微信小程序、微信公众号、支付宝小程序等，应统一映射为后台可理解的渠道枚举。
- 分账渠道配置应为后台可维护配置，不写死在代码中。

## 2. 当前新分账逻辑概览

当前新分账链路已经与旧分账结果表隔离：

- 支付前调用 `RevenueCalculator`。
- 分账结果写入 `revenue_order`。
- 支付成功结算读取 `revenue_order`。
- 退款前置拆分与退款成功扣回读取 `revenue_order`。
- 账户管理人后台查询读取 `revenue_order`。

当前计算顺序：

1. 先识别设备出租：商品组织 `sod_ao_id` 与订单收款组织 `order.ao_id` 不同。
2. 再识别设备分账：设备绑定 `revenue_rule.rule_mode=3` 策略。
3. 若没有设备分账策略，则生成普通分账。

当前主要限制：

- 设备出租比例写死为 100%。
- 分账是否生效未按收款渠道配置控制。
- 设备出租策略未抽象成可配置规则。
- 设备出租和设备分账同时生效时，基数和优先级仍需进一步明确。

## 3. 优化点清单

| 优先级 | 优化点 | 当前状态 | 建议处理 |
| --- | --- | --- | --- |
| P0 | 增加收款渠道分账开关 | 当前所有进入支付前分账入口的订单都会尝试生成分账 | 新增渠道配置表或策略字段，计算前先判断渠道 |
| P0 | 设备出租分账比例配置 | 当前固定 100% | 设备出租使用 `revenue_rule` + `revenue_rule_item` 配置比例 |
| P0 | 设备出租策略匹配维度 | 当前只按商品组织和订单组织不同自动触发 | 支持按设备、收款组织、商品组织匹配策略 |
| P1 | 设备出租与设备分账并存时基数控制 | 当前设备分账可按订单总额或扣除出租金额，依赖 `base_type` | 明确默认扣除出租已分账金额，避免超额 |
| P1 | 分账总额封顶 | 当前策略校验有比例控制，但运行时缺少统一封顶保护 | 计算服务增加订单级、子订单级分账总额校验 |
| P1 | 幂等状态保护 | 当前生成前按订单删除旧 `revenue_order` | 只允许删除待支付记录，已结算或已退款记录不允许覆盖 |
| P1 | 阶梯营业额统计性能 | 当前实时汇总 `sale_orders` | 中长期可引入月度设备营业额汇总表 |
| P1 | 阶梯跨档计算 | 当前按本单后累计整单命中 | 后续支持跨阶梯拆分 |
| P2 | 退款分摊精度 | 当前按比例扣回，存在四舍五入差额 | 最后一笔退款吸收尾差 |
| P2 | 非余额账户结算状态 | 当前非余额型只更新状态，不真实打款 | 增加第三方分账/打款状态和失败原因 |
| P2 | 后台配置可解释性 | 当前配置项偏底层 | 后台增加场景化配置页和试算功能 |

## 4. 重点优化方案

### 4.1 收款渠道分账开关

#### 方案 A：新增全局渠道配置表

新增表 `revenue_pay_channel`：

```sql
CREATE TABLE `revenue_pay_channel` (
  `rpc_id` int NOT NULL AUTO_INCREMENT COMMENT '分账收款渠道配置ID',
  `pay_type` int NOT NULL COMMENT '订单支付类型',
  `payee_type` int DEFAULT NULL COMMENT '收款策略支付类型',
  `channel_name` varchar(50) DEFAULT NULL COMMENT '渠道名称',
  `status` tinyint(1) DEFAULT 1 COMMENT '状态：1启用分账，2停用分账',
  `creator` int DEFAULT NULL,
  `create_time` int DEFAULT NULL,
  `update_time` int DEFAULT NULL,
  PRIMARY KEY (`rpc_id`),
  UNIQUE KEY `uk_pay_type` (`pay_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='需要分账的收款渠道配置表';
```

计算前判断：

```text
订单 pay_type / 收款策略 payee_type 命中启用配置 -> 生成 revenue_order
未命中 -> 不生成 revenue_order，支付继续
```

优点：

- 配置集中，后台易维护。
- 对所有设备、组织统一生效。
- 上线风险低。

缺点：

- 不支持不同组织设置不同渠道口径。

#### 方案 B：使用独立收款策略新分账配置

新增独立表 `revenue_payee_config`，使用 `sp_id` 关联实际收款策略：

计算前判断：

```text
当前订单实际使用的 sp_id 对应 revenue_payee_config.enable_revenue=1 -> 生成 revenue_order
否则 -> 不生成 revenue_order
```

优点：

- 可精确控制到每个收款策略。
- 适合不同组织、不同设备使用不同收款策略的场景。

缺点：

- 如果同一个渠道有多个收款策略，需要逐个维护。
- 不如全局渠道配置直观。

#### 推荐

推荐采用组合方案：

- 新增 `revenue_pay_channel` 作为全局渠道开关。
- `revenue_payee_config.enable_revenue` 作为策略级覆盖开关。
- 最终判断为：渠道启用且收款策略启用，才生成分账。

影响：

- 需要新增后台配置页面。
- 支付前分账入口需增加渠道判断。
- 未启用分账渠道的订单不会生成 `revenue_order`，账户管理人后台也不会看到分账订单。

### 4.2 设备出租分账比例配置

#### 方案

将设备出租纳入 `revenue_rule`：

- `revenue_rule.rule_mode=2` 表示设备出租策略。
- 规则按设备绑定，不再按代收组织区分适用范围。
- `revenue_rule_item.receiver_ao_id` 表示商品组织。
- `calc_type=1` 表示按比例。
- `calc_value=100` 表示全额分账。
- `calc_value=80` 表示 B 获得商品交易金额 80%。

设备绑定：

- 继续使用 `revenue_rule_machine` 绑定设备和设备出租策略。
- 也可允许组织级默认出租策略，但 V1 建议先按设备绑定，避免范围过大。

计算规则：

```text
当 A 设备销售 B 商品：
1. 查找该设备绑定的 rule_mode=2 出租策略。
2. 在策略明细中查找 receiver_ao_id=B 的规则。
3. 按该明细 calc_type/calc_value 计算 B 分账金额。
4. 若未找到 B 的出租策略明细，按业务配置决定：
   - 严格模式：支付前报错。
   - 宽松模式：不生成 B 分账。
```

推荐采用严格模式：

- A 代收 B 商品，如果 B 分账比例未配置，支付前报错。
- 避免已代收但无法解释分账归属。

影响：

- 当前固定 100% 的设备出租记录会变成配置驱动。
- 后台需要支持设备出租策略配置。
- 原有“只要商品组织不同就全额分账”的自动行为会变化。
- 测试用例需要覆盖 100%、非 100%、未配置三种情况。

### 4.3 设备出租与设备分账的金额关系

问题：

- 一笔订单中可能同时存在 B 组织出租商品和设备分账策略。
- 如果 B 商品已按出租策略分走一部分金额，设备分账再按订单总额计算，可能导致分账总额超过订单金额。

建议默认规则：

```text
设备出租分账先计算。
设备分账基数默认使用：订单总额 - 已生成的出租分账金额。
```

保留策略字段 `base_type`：

- `1`：订单总额。
- `2`：扣除出租分账金额后的剩余金额。

推荐默认：

- `base_type=2`

影响：

- 可避免大多数超额分账。
- 如果业务确实要求设备分账按订单总额计算，需要后台明确提示可能超额，并增加总额封顶校验。

### 4.4 分账总额封顶

建议在 `RevenueCalculator` 保存前增加统一校验：

- 按订单维度统计所有 `income_amount` 合计。
- 合计不能超过 `order.total_price`。
- 按子订单维度统计出租分账合计。
- 子订单出租分账不能超过该子订单金额。

如果超过：

- 支付前返回错误，不生成分账订单。

影响：

- 能提前暴露错误配置。
- 会阻断部分历史上可能“配置不合理但仍能支付”的订单。
- 需要后台配置页增加比例合计提示，减少运营配置错误。

### 4.5 幂等与已结算保护

当前 `RevenueCalculator::saveRecords()` 会按 `order_id` 删除旧 `revenue_order` 后重建。

风险：

- 如果异常重复调用发生在支付成功后，可能删除已结算记录。
- 如果已发生退款，再重建会丢失 `refund_amount`。

建议优化：

```text
1. 若订单已有 status=1/2/3 的 revenue_order，禁止重算并返回错误。
2. 仅允许覆盖 status=0 的待支付记录。
3. 支付取消可将 status 更新为 4，而不是删除。
```

影响：

- 提升财务记录安全性。
- 需要明确支付失败、支付撤销、重新支付时的状态流转。

### 4.6 阶梯营业额汇总

当前每次计算阶梯都实时查询 `sale_orders` 当月营业额。

风险：

- 订单量大时支付前计算变慢。
- 并发支付时，本单前累计营业额可能存在竞争。

优化方案：

- 新增 `revenue_machine_monthly_turnover` 汇总表。
- 支付成功后累加营业额。
- 退款成功后扣减净营业额。
- 阶梯计算读取汇总表，并在必要时加锁。

影响：

- 支付前计算性能更稳定。
- 实现复杂度增加。
- 需要处理补偿任务和数据校准。

V1 建议：

- 先保留实时统计。
- 增加索引：`sale_orders(m_id, pay_status, pay_time)`。
- 后续订单量上来后再引入汇总表。

## 5. 数据结构调整建议

### 5.1 新增分账渠道配置表

```sql
CREATE TABLE IF NOT EXISTS `revenue_pay_channel` (
  `rpc_id` int NOT NULL AUTO_INCREMENT COMMENT '分账收款渠道配置ID',
  `pay_type` int NOT NULL COMMENT '订单支付类型',
  `payee_type` int DEFAULT NULL COMMENT '收款策略支付类型',
  `channel_name` varchar(50) DEFAULT NULL COMMENT '渠道名称',
  `status` tinyint(1) DEFAULT 1 COMMENT '状态：1启用分账，2停用分账',
  `creator` int DEFAULT NULL,
  `create_time` int DEFAULT NULL,
  `update_time` int DEFAULT NULL,
  PRIMARY KEY (`rpc_id`),
  UNIQUE KEY `uk_pay_type` (`pay_type`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='需要分账的收款渠道配置表';
```

### 5.2 独立收款策略新分账配置

不修改 `strategy_payee`。使用独立的 `revenue_payee_config` 保存：

- 实际收款策略 `sp_id`
- 默认分账账户和账户管理人
- 新分账启用状态

### 5.3 设备出租策略复用现有新表

无需新增出租专用表，复用：

- `revenue_rule`
- `revenue_rule_item`
- `revenue_rule_machine`

配置示例：

```text
revenue_rule:
  rule_mode=2
  rule_name=A设备出租给B商品分账

revenue_rule_item:
  receiver_ao_id=B组织ID
  ra_id=B组织分账账户
  calc_type=1
  calc_value=100
```

## 6. 后台原型/配置调整

### 6.1 收款渠道分账配置

新增页面：分账渠道配置。

字段：

- 渠道名称。
- 订单支付类型 `pay_type`。
- 收款策略类型 `payee_type`。
- 是否启用分账。
- 创建人、更新时间。

操作：

- 新增渠道。
- 编辑渠道。
- 启用/停用。

### 6.2 收款策略配置

新增字段：

- 默认分账账户。
- 默认账户管理人。
- 是否启用新分账。

交互：

- 如果渠道未启用分账，默认分账账户可不强制。
- 如果渠道启用分账且收款策略启用分账，必须选择默认分账账户。

### 6.3 设备出租策略配置

在分账策略页面新增“设备出租”模式：

- 选择代收组织 A。
- 添加商品组织 B。
- 选择 B 的分账账户。
- 设置 B 的分账比例，允许 100%。
- 绑定设备。

校验：

- 比例范围 `0 < calc_value <= 100`。
- 分账账户所属组织必须等于商品组织。
- 同一设备、同一商品组织不能存在多个启用出租策略明细。

## 7. 开发影响分析

### 7.1 后端影响

需要调整：

- `RevenueCalculator`
  - 增加收款渠道分账开关判断。
  - 设备出租从固定 100% 改为读取 `rule_mode=2` 策略。
  - 增加分账总额封顶。
  - 优化 `saveRecords()` 幂等保护。
- 管理端 Revenue 模块
  - 增加分账渠道配置接口。
  - 设备出租策略配置支持比例。
  - 策略校验增加出租策略维度。
- 独立新分账配置模块
  - 使用 `revenue_payee_config.enable_revenue`。
  - 根据渠道配置决定是否要求默认分账账户。
- 数据库脚本
  - 新增 `revenue_pay_channel`。
  - 新增或维护 `revenue_payee_config`，不修改 `strategy_payee`。

预计工作量：

- 分账渠道配置：1-2 人日。
- 设备出租比例配置：2-3 人日。
- 计算器调整和封顶校验：2-3 人日。
- 幂等保护：1 人日。
- 联调测试：2-3 人日。

后端合计：8-12 人日。

### 7.2 前端影响

需要新增或调整：

- 分账渠道配置页面。
- 收款策略表单增加是否启用分账。
- 设备出租策略表单增加比例配置。
- 分账策略列表增加模式筛选和展示。
- 配置错误提示和比例合计提示。

预计工作量：

- 分账渠道配置页面：1-2 人日。
- 收款策略表单调整：0.5-1 人日。
- 设备出租策略配置：1-2 人日。
- 联调修复：1-2 人日。

前端合计：3.5-7 人日。

### 7.3 测试影响

新增测试场景：

1. 渠道启用分账，订单生成 `revenue_order`。
2. 渠道停用分账，订单不生成 `revenue_order`，支付继续。
3. 收款策略停用分账，订单不生成 `revenue_order`。
4. A 设备销售 B 商品，B 配置 100%，B 获得商品全额。
5. A 设备销售 B 商品，B 配置 80%，B 获得商品金额 80%。
6. A 设备销售 B 商品，B 未配置出租策略，严格模式下支付前失败。
7. 出租分账 + 设备分账并存，验证设备分账基数扣除出租金额。
8. 分账总额超过订单金额，支付前失败。
9. 重复发起支付，不覆盖已结算或已退款分账记录。

### 7.4 上线影响

上线前需要：

- 初始化需要分账的收款渠道。
- 为现有收款策略补充 `enable_revenue` 默认值。
- 为设备出租场景配置 `rule_mode=2` 策略。
- 灰度选择少量设备验证。

兼容影响：

- 未配置为需要分账的渠道，不会再生成新分账订单。
- 设备出租不再天然全额分账，取决于后台策略配置。
- 如果采用严格模式，缺少出租策略会阻断支付。

### 7.5 财务影响

正向影响：

- 设备出租分账从固定全额变为合同化比例，财务口径更灵活。
- 收款渠道可控，避免不应分账的渠道产生分账记录。
- 分账总额封顶后，可避免配置错误造成超额分账。

潜在风险：

- 渠道配置错误会导致应分账订单未生成分账。
- 出租比例配置错误会直接影响 B 组织收入。
- 严格模式下，配置缺失会阻断支付，需要运营提前配置完整。

建议：

- 增加配置变更日志。
- 增加分账试算功能。
- 增加“今日应分账但未生成”巡检报表。

## 8. 推荐实施顺序

1. 新增收款渠道分账配置。
2. 收款策略增加 `enable_revenue`。
3. `RevenueCalculator` 增加渠道判断，未命中时直接跳过分账。
4. 设备出租改为读取 `rule_mode=2` 策略比例。
5. 增加分账总额封顶。
6. 优化 `saveRecords()` 幂等保护。
7. 调整后台配置页面。
8. 补充测试用例和灰度验证。

## 9. 结论

当前新分账逻辑的方向是正确的：已做到独立新表、独立计算、独立后台查询。但为了满足新增业务规则，需要优先补齐两个能力：

1. 收款渠道是否参与分账必须后台可配置。
2. 设备出租分账比例必须策略化，100% 只是配置值，不应硬编码。

这两项会改变分账生成条件和设备出租金额计算口径，属于 P0 级优化。建议在继续扩大联调前先落地，否则后续订单数据会按旧口径生成，产生财务校正成本。
